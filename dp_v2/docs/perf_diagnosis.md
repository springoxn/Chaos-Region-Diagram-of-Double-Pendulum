# 性能诊断（基准测试结果）

## 实测数据

| 测量项 | 结果 |
|---|---|
| 单轨迹积分吞吐 | 4.55–4.67 μs/步 |
| `dp_lyap` 单次调用固定开销 | **≈ 0.07 s** |
| 并行加速比（12 workers，12×12 网格） | **仅 1.6×** |
| 受迫摆默认工作量 | 旧探针的 **25 倍步数** |

## 三个独立的慢因

### 1. 逐点调用 `dp_lyap`，固定开销乘以网格点数（主因）

每个网格点调用一次 `dp_lyap`，每次调用有约 0.07 s 的固定开销
（参数校验、结构体解析、闭包、`qr` 初始化）。

N=60 网格 = 3600 点 → **约 250 秒纯粹消耗在调用开销上**，与积分本身无关。

### 2. 每个点、每一步都调 `qr()`

最大指数只需要一个切向量，但当前实现对 4×1 向量调用 `qr(Q,0)`。
对向量而言这只是归一化，`qr` 的函数开销远超运算本身。

### 3. 没有跨点向量化

**原项目比现在快的关键**：原 `compute_row` 把**一整行 N 个初值**放进
1×N 向量，用矩阵运算同步推进——一步的开销摊到 N 个点上。

现在的实现是逐点标量推进，完全放弃了这一优势。

### 4. parfor 粒度太细

按行 parfor，每行工作量小，12 workers 只有 1.6× 加速。

## 修复方向

| 问题 | 对策 | 预期 |
|---|---|---|
| 1 | 跨行向量化 + 批量 API | 消除 250 s 开销 |
| 2 | 单指数时用显式归一化替代 `qr` | 每步省一次函数调用 |
| 3 | 4×N 状态与 4×N 切向量同步推进 | 一步开销摊到 N 点 |
| 4 | 增大 parfor 粒度（按行块） | 接近线性加速 |
| — | 分挡位（preview/standard/accurate）+ 两趟细化 | 交互场景再快 5–10× |

**不可压缩的部分**：真实 Lyapunov 指数需要 T ≫ 1/λ 的积分，这一步不能省。
优化针对的是"实现开销"，不是物理本身。
